# Top 5 台本・音声生成ルール

最終確認日: 2026-10-25

## 台本

- 想定リスナーは、このサイトを個人利用するエンジニア本人とする。ソフトウェア、インフラ、AI、セキュリティの基礎語彙と、数字を比較して考える習慣は共有済みとして扱う。一方、専門外の科学、経済、制度、個別業界については、理解に必要な橋渡しを省かない。
- 基礎用語を「XとはYです」と初学者向けに定義する話し方は避ける。「確保したメモリ領域の外へ書く、いわゆる範囲外書きが起きると」のように、概念を短く再提示し、そのまま今回固有の原因、影響範囲、悪用条件、対策へ進む。聞き手が知っていることを試す表現や、知らないことを責める表現にはしない。
- 「ご存じの通り」を多用せず、知識を前提にした自然な接続で示す。説明を省略するのではなく、一般論を短くして差分へ説明量を使う。用語の辞書的意味より、「今回はどこが普通と違うか」「実務で何を変えるか」「似た事例と何が違うか」を優先する。
- エンジニアの関心に合わせ、可能ならアーキテクチャ、障害モード、トレードオフ、スケール、観測可能性、運用コスト、セキュリティ境界、導入条件のいずれかへ接続する。技術と直接関係しない記事でも、数値の読み方、因果と相関、制度設計、供給網など再利用できる思考の型を一つ持ち帰れるようにする。
- 元記事の論調や結論を正しい前提で補強しない。記事内の中心的な主張を、確認可能な事実、当事者の説明、記者や研究者の解釈、因果関係の推定、将来予測に分け、それぞれを別の一次資料または独立した信頼できる情報源で照合する。
- 解説はファクトチェックを兼ねる。数字の母数と期間、比較対象、調査方法、記事が省略した条件、発表主体の利害、反証可能性を確認し、確認できた範囲と確認できなかった範囲を明示する。タイトルやプレスリリースの表現を、そのまま客観的事実として読まない。
- 有力な反論、別の因果説明、異なるデータ、影響を受ける側の異なる視点があれば、元記事の主張と合わせて紹介する。完全な反論でなくても、結論が変わり得る条件や別の評価軸として扱う。反対意見を探した結果、有力なものが確認できなければ無理に作らない。
- 中立性は、賛成と反対へ同じ秒数を割り当てることではない。根拠の量、一次性、方法の妥当性、再現性に応じて重みを付ける。科学的合意と根拠の乏しい主張、確認済み事実と当事者の宣伝を同格に並べる偽のバランスは避ける。
- 検証の結果、記事の主張が一次資料や独立した資料で十分に裏付けられた場合は、その結論を明確に支持し、追加根拠や適用範囲を示して補強してよい。中立性を演出するためだけの反論、留保、両論併記は加えない。
- Hacker News、Reddit、はてなブックマーク、専門家の投稿などで、支持を集めた反応、繰り返し出る疑問、技術的に重要な指摘、記事と異なる有力な視点があれば確認する。コメントは事実の根拠ではなく、追加検証すべき論点を見つける手掛かりとして扱う。
- 反応を紹介するときは、どの場でどの程度注目されたかを可能な範囲で示し、全読者や社会全体の意見へ一般化しない。賛同数の多さだけで採用せず、記事理解を深める具体性と検証可能性を優先する。確認後に正しければ補足し、誤解なら責める調子を避けて訂正し、判断が割れるなら前提の違いを説明する。
- 最終的な説明は「記事はこう主張する」「ここまでは別資料でも確認できる」「ただしこの因果関係には別の説明がある」「現時点ではどちらがどの程度妥当か」の順を基本とする。判定できない場合は曖昧に丸めず、判定に欠けているデータを具体的に示す。
- 順位は読み上げない。タイトルの直後に、確認できた反響の数値または事実を1文だけ置く。
- 結論が分かりにくい記事は結論を先に示す。概要、注目理由、解説で同じ結論を言い換えない。
- 1記事の担当は最大3役に限る。「紹介役」はタイトル、反響、結論、「解説役」は事実関係と基礎解説、「追加視点役」は客観評価と先回り質問を担当する。
- 各情報、判断、注意点は原則1回だけ話す。先回り質問は本文で未回答の実用的な疑問に限る。
- 先回り質問は必須ではない。解説や追加視点ですでに答えた内容を疑問形に直して繰り返さない。前段にない具体的な数値、実用上の境界、費用、期間、比較対象などを追加できる場合だけ採用する。
- 先回り質問には、その時点で最も妥当な答えを先に示す。「総合的に判断する必要がある」のように判断材料だけを並べて終えない。不確実な場合も、何が未確定かを述べたうえで、「Aのため予測は難しいものの、Bのため短期的にCとなる可能性は低い」のように、確認済みの事実から導ける見通し、確率の方向、時間軸、または条件付き結論を示す。
- 先回り質問を「ここで気になるのは」のような同じ導入句で始めない。前文から自然につなぐか、質問そのものを短く提示する。答えが「不明」「確定していない」だけになる質問は採用せず、確認済みの条件、比較可能な過去事例、概算、または判断に使える範囲を示す。信頼できる参考値が一つもない場合は、その質問を台本へ入れない。
- 専門用語は定義、具体像、重要性、未確定点、判断軸まで説明する。長さではなく新しい理解を増やす。
- 各記事で「なぜ今起きたのか」を確認する。発表主体の狙い、直前の出来事、需給・制度・事業上の背景、予定済みの次工程を調べ、単なる出来事の要約で終えない。公式に示された理由、報道機関の分析、編集上の推論を区別し、戦争、AI、業績悪化などを根拠なく原因へ結び付けない。
- 個別企業の人員削減、投資、撤退は、その会社だけの事情か業界全体の動きかを確認する。同業または隣接業界の2〜3社と比較し、共通する資本・人員の移動と会社固有の事情を分ける。「AIによる解雇」のような単一原因へまとめず、自動化、設備投資への資金移動、採用反動、管理階層の整理、需要変化のうち、裏付けられたものだけを述べる。
- 海外の重要物資、制裁、産業政策は、日本へ届く経路まで確認する。主要輸入先、国内企業が示す直近の供給量・価格・納期、政策が融資・監視・備蓄・輸出規制のどれなのか、医療・交通・研究・製造など用途別の影響差を調べる。国内優先や用途間の奪い合いは制度的根拠を確認し、確認できない優先順位は作らない。
- 記事の中心から一段だけ外側へ広げ、同業他社、海外から日本への波及、隣接用途、代替技術のどれかを加える。ただし、元記事と関係の薄い一般論を足さず、出典で裏付けられ、聞き手の判断や見通しを具体的に変える情報に限る。
- 既に次の候補、日程、選考、後継サービスがある場合は「未定」でまとめず、何が決まり、何が選考中で、いつ確定するのかまで説明する。
- 情報源の主張、確認済みの事実、編集上の推論を区別する。「原文では」は比較や評価につながる場合だけ使う。
- 4人のキャスタープールから、1記事につき3人を選ぶ。各キャスターはその記事で1区間までとし、細かく交代させない。掛け合いや相づちは作らず、紹介・解説・追加視点の担当順と休む1人を記事ごとにずらす。
- 役割を変えて同じ説明を言い換えない。記事内の全区間を通して同一文を除き、各役は前の役にない情報または判断軸を一つ以上加える。
- ずんだもんの「のだ」は担当区間の冒頭または末尾を中心に使い、連続させない。
- 書き言葉の「である」調を避け、ニュース読みとして自然な「です・ます」調にする。
- キャスターの区間は「確定しない」「重要になる」のような常体で終えず、「確定しません」「重要になります」のような自然な敬体にする。
- 「ここが、この話題を見るうえでのポイント」のような内容を増やさない決まり文句は加えない。ずんだもんの「のだ」は、直前の文末を自然に言い換えて付け、独立した締め文句を追加しない。
- 英字を含む製品名、サービス名、ライブラリ名、団体名、略語は読みを推測しない。公式サイト、公式の日本語表記、開発元・作者の発音案内を優先して確認し、`config/pronunciations.json` に登録してから台本を確定する。一次情報に発音がなければ、複数の信頼できる用例を照合し、不確実性を記録する。
- 英語名は一般的な和製カタカナへ機械的に置き換えず、原語の発音、強勢、母音、語末の響きに近いカタカナ列を作る。VOICEVOXで試聴し、原音への近さと日本語文中での聞き取りやすさを両立させる。略語は現地で一語読みするのか、文字ごとに読むのかも確認する。
- 一つの英語名や略語の読みの途中に `・` や読点を入れない。文字ごとに読む略語も「ユーアールエル」のようにつなげ、`AP通信` のように後続の日本語との境目が不自然になる語は複合語全体を辞書へ登録する。試聴では各音の正しさだけでなく、語中に不自然な間がないことも確認する。
- 原語に近い発音と日本で定着した呼称が大きく異なる場合は、最初の登場時だけ「ブロットリ、日本ではブロトリと呼ばれる」のように本文へ短く織り込む。その後は原語に近い発音へ統一し、日本での呼称を毎回言い直さない。
- 台本生成時に未登録の英字語が一つでも残った場合は生成を失敗させる。漢字の誤読は試聴時にも確認し、見つけた複合語を文脈込みで読み辞書へ追加する。

## 記事本文との共通ルール

- 記事本文も台本と同じく、読者が結論を先に理解できる順序にする。
- 記事の構造化詳細欄は「結論」「何が分かったのか」「背景」「基礎からの解説」「読者にとっての意味」「注意点・未確定事項」「次に確認すること」で構成する。
- 台本は記事本文を薄く言い換えるためのものではない。Top 5では原文を再確認した追加情報を台本へ加えられるが、記事本文にも有用な内容は構造化詳細欄へ戻す。
- 概要、解説、詳細欄、台本の各部分で同じ結論や注意書きを繰り返さず、それぞれ新しい理解を一つ以上増やす。

## Podcastとしての編集方針

- 番組の価値を「5件を短く知ること」だけに置かない。各ニュースを入口に、背景となる制度・産業構造・科学知識、日本への波及、比較できる他事例、今後を見る指標のうち、最も有用なものを一段深く説明する。
- 一般向けの教養番組ではなく、専門外も効率よく理解したいエンジニア向けの教養Podcastとする。既知の技術概念は一文で再起動し、ニュース固有の差分や応用へ時間を使う。専門外の領域は前提を飛ばしすぎず、エンジニアが既存知識へ接続できる比喩、構造、数値比較を使う。
- 1トピックは「何が起きたか」「周辺をどう理解すればよいか」「この先をどう見るか」の3層で構成する。3人の担当はこの層に対応させてもよいが、役割名を読み上げず、同じ説明を別の言葉で繰り返さない。
- 元記事の要約が主で、解説が付録になる構成を避ける。元記事だけでは答えにくい素朴な疑問を一つ選び、追加取材で具体的な答えまたは条件付きの見通しを示す。
- 周辺知識は際限なく広げず、中心ニュースとの因果関係を1文で説明できる範囲に留める。1トピックで増やす論点は原則2つまでとし、数字・比較・仕組みのいずれかを必ず含める。
- 事実、発表主体の見解、報道機関の分析、編集上の推論を音声でも聞き分けられる表現にする。推論は根拠と条件を添え、断定調で事実のように読まない。
- 番組は取り上げた記事の応援や批判を目的にしない。記事の主張を入口に、裏付け、反証、別解釈、当事者ごとの利害を検討し、聞き手が自分で判断できる材料を増やす。
- コメント欄やコミュニティの反応は、注目度の紹介だけで終えず、聞き手が抱きそうな疑問、専門家が気付いた例外、広がっている誤解を選ぶ。採用した反応には追加調査で答え、単なる感想の読み上げや論破の材料にはしない。
- 番組説明と各エピソード説明に、VOICEVOXによる合成音声を使用していることと全話者のクレジットを明記する。音声末尾の読み上げクレジットも維持する。
- 訂正は元エピソードを黙って差し替えず、軽微な修正は説明欄へ追記し、理解を変える訂正は次回冒頭または短い訂正エピソードでも告知する。GUIDは変更しない。
- Podcast配信の技術要件、RSS、音声ホスティング、アートワーク、AI音声表示は `docs/podcast-distribution-policy.md` に従う。

## VOICEVOXと音源の公開条件

- 使用音源ごとに `VOICEVOX:満別花丸`、`VOICEVOX:ずんだもん`、`VOICEVOX:四国めたん`、`VOICEVOX:冥鳴ひまり` を省略せず表示する。
- クレジットはサイト、RSS説明、M4Aメタデータへ入れる。単体音声でも分かるよう末尾でVOICEVOX利用を読み上げる。
- VOICEVOXソフトウェア、モデル、キャラクター素材を再配布しない。音声とイラストの利用条件を混同しない。
- 満別花丸について、公序良俗違反、反社会的勢力、特定政党・政治家の極端な賞賛・批判、他者に損害を与える用途、悪意ある加工、公式を装う用途には使わない。
- ずんだもん・四国めたんについて、政治・宗教活動、特定個人・団体・国家の非難・批判・応援を目的とする内容、情報商材、意図的な虚偽・誤解誘導、禁止業種、反社会的勢力の用途には使わない。
- 冥鳴ひまりについて、公序良俗に反する行為、第三者に不利益・損害を与える行為、特定の思想・団体に当たる行為、権利者が不適切と判断する用途には使わない。
- Top 5に上記へ触れる記事がある場合は、Codexが目的と表現を慎重に確認し、必要なら対象音源を使わない。事実報道かどうかだけで安全とみなさない。この通常レビューだけを理由にユーザー確認を求めず、本人にしか確定できない権利・事実の判断が不可欠な場合だけ停止する。
- 規約は変更され得るため、公開前に公式規約の更新日と内容を再確認する。

## BGM

- `assets/audio/bgm/` の曲は、Suno有料プラン契約中にユーザー自身が生成し、正規にダウンロードした専用音源だけを登録する。
- 他者の曲のRemix、第三者の歌詞・録音・権利未確認素材を含む曲は登録しない。生成・ダウンロード時の契約記録をリポジトリ外で保管する。
- BGM原本は直接公開せず、読み上げへ18〜24 dB下げて混合し、AACへ変換した完成物だけを配信する。
- 記事テーマに合う候補曲を絞り、その候補内で日付と記事を種に選曲する。同じテーマでも日ごとに変化させ、同じ日の再生成は再現可能にする。曲の重複回避よりテーマ適合を優先する。記事間ではBGMをフェードアウトしてジングルを鳴らし、次の記事から別のBGMをフェードインする。
- 公開物には `BGM制作・利用権管理: floortable（Suno有料プラン生成）` と表示する。これはSunoの後援や公式制作を示す表記ではない。
- BGMファイルにはMIT Licenseを適用せず、第三者へ原本の再利用権を与えない。
- トピック切替SEもSuno有料プラン生成素材としてBGMと同じ権利管理を行い、原本を直接配信しない。記事間では先頭1.0秒を音量調整して使用する。
- Sunoの規約上、有料プランで生成・正規ダウンロードした曲は商用利用できるが、著作権の成立を保証するものではない。公開先の規約も別途守る。

## 公開前チェック

1. 台本の事実確認、重複、読み、禁止用途への該当をCodexが確認する。英字の製品名・ライブラリ名は確認根拠のある読みが辞書へ登録され、未登録語チェックが通っていることを必須とする。通常の確認は自動実行し、ユーザーに承認を求めない。
2. VOICEVOXと各音源の公式規約を再確認する。
3. クレジットが音声末尾、メタデータ、サイト、RSSにあることを確認する。
4. BGM原本が公開ディレクトリへコピーされていないことを確認する。
5. `npm run validate:data`、`npm test`、`npm run build`、各種checkをすべて通す。
6. 完成したM4Aを試聴・再生確認してから `config/published-media.json` へ追加する。
7. M4Aは `moov` を先頭へ配置し、公開URLのRange応答とPC・iOS系ブラウザーでのストリーミング再生を確認する。
