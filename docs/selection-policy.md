# 記事選定ポリシー

このサイトの目的は、国内外で実際に話題になっている出来事を横断し、普段の守備範囲外に出会える一般ニュースを1日30件前後、日本語で届けることである。ニュース記事に限らず、社会的・文化的な広がりを確認できるミーム、バズ動画、流行音源、ダンスや言い回しも対象にする。これとは別に、実務上継続して追う必要があるVCF・VMware関連ニュースを専門枠として0〜5件掲載する。国や地域を先に割り当てず、内容の面白さ、重要性、話題性、分野の広がりで選ぶ。

人気順をそのまま転載せず、人気指標を発見の入口として使う。掲載内容の正確性、出典、日付、権利は、人気とは別に確認する。

## 毎日の基本構成

一般ニュースは30件前後を目安とし、通常は25〜35件程度とする。ただし、件数を満たすために弱い記事を採用したり、上限へ合わせるために重要な記事を落としたりしない。ニュースの質と重複除外の結果によって、この範囲を外れることも許容する。VCF専門枠は一般ニュースの件数に含めない。

| 発見経路 | 目安 | 役割 |
| --- | ---: | --- |
| Hacker News | 4〜8件 | 技術に限定せず、科学、ビジネス、教育、文化などを拾う |
| はてなブックマーク | 4〜8件 | 日本語圏で共有・議論されている社会、生活、文化、技術などを拾う |
| ソーシャル発見 | 4〜8件 | Reddit、4chan、Lobsters、Bluesky、Mastodon、Togetter、TikTok、YouTube、Instagram Reels、ニコニコなどから、生活、文化、趣味、地域、人物、ネット文化を拾う |
| 横断媒体 | 3〜6件 | GIGAZINEなどから、分野をまたぐ話題や元記事への入口を得る |
| 一般報道・一次情報 | 8〜12件 | 大きなニュースの確認と、ランキングだけでは拾いにくい重要事項を補う |

同じ記事が複数経路に現れた場合は1記事として数え、該当する経路をすべて記録する。発見経路は出典ではない。必ず原文、公式発表、信頼できる報道などの個別ページを確認する。

## 地域の扱い

日本、海外、特定地域の件数枠は設けない。地域ではなく内容で判断し、その結果として海外記事または日本の記事が多くなることは許容する。ただし、一つの国や英語圏だけへの偶発的な集中が、収集元の偏りによるものではないかを最終レビューで確認する。日本語記事が見つからないことを不採用理由にせず、原文を確認して日本語で要約する。紹介記事を入口にした場合は、可能な限り元記事、論文、公式発表まで遡る。

## ソーシャル発見の扱い

- Togetter、Reddit、4chanなどは「何が話題か」を見つける入口であり、投稿内容だけを事実確認の根拠にしない。
- Togetterでは、まとめられた投稿の文脈、元投稿、恣意的な抜粋の可能性を確認する。
- Redditでは、サブレディット名、投稿日時、スコア、コメント数、元リンクを確認し、再投稿や同一題材の重複を除く。
- 4chanでは、板名、スレッド確認時刻、返信数を記録できる場合だけ候補化する。匿名の主張、リーク、個人特定情報は、独立した一次資料または信頼できる報道で裏付けられない限り掲載しない。
- 投稿やスレッドが削除される可能性を前提とし、削除済みコンテンツの転載、アーカイブ回避、アクセス制限の回避は行わない。
- 個人晒し、住所・連絡先などの個人情報、差別扇動、嫌がらせ、違法性の疑われる画像、性的搾取、残虐画像は採用しない。
- ミーム、創作、ジョーク、風刺は、事実報道と混同しない形でネット文化や反応として扱う。
- ソーシャル上の反応を一般世論と表現しない。「特定コミュニティで話題」と範囲を限定する。

## ミーム・バズ動画・流行音源

件数ノルマは設けない。十分な広がりと説明価値を確認できたものだけを一般ニュース枠へ含め、流行しているように見えるだけの転載、広告、仕込み、単一アカウント内だけの人気で枠を埋めない。

- TikTok、YouTube、YouTube Shorts、Instagram Reels、X、Bluesky、Mastodon、Reddit、Twitch clips、ニコニコ、Bilibiliなどを候補発見に使う。
- 最初の投稿者、投稿先、投稿日時、元URLを可能な限り一次投稿で確認する。まとめ記事や転載動画を「発祥」と扱わない。
- 起源が割れている場合は「起源に異説あり」、元投稿を確認できない場合は「未特定」と明記し、最古と断定しない。
- 元ネタとなる作品、映像、画像、セリフ、ゲーム、出来事を確認し、後付けの説明や誤帰属を区別する。
- BGM、楽曲、音声、サンプリング素材は、公式音源ページ、クレジット、権利者情報などで照合する。音源認識だけの場合は「有力候補」にとどめる。
- どのプラットフォームへ、どの順番で、どのような派生形式として広がったかを確認時刻付きで記録する。再生数等は実測できた値だけを使う。
- 好意的な二次創作、批判、飽和、企業利用、逆輸入など反響の種類を分ける。大きな再生数を支持や社会的重要性と同一視しない。
- 動画、音源、画像、歌詞、字幕、サムネイルを転載しない。原則として元投稿と公式素材へのリンクで説明する。
- 個人を嘲笑する失敗動画、未成年者、事故、医療状態、私的場面、ディープフェイク、晒し、嫌がらせは、本人の尊厳と二次被害を優先し、人気があっても原則採用しない。
- 広告案件、キャンペーン、意図的なシーディングが確認できる場合は自然発生の流行と区別する。

## 分野のバランス

一般ニュース全体では次を目安とする。件数は30件を想定した参考値であり、総数が増減する日は比率と全体の読み味を優先する。該当ニュースが乏しい分野を無理に埋めず、編集メモに理由を残す。

- 社会・政治・国際: 4〜6件
- 経済・仕事・ビジネス: 3〜5件
- テクノロジー: 3〜5件
- 科学・医療・環境: 3〜5件
- 暮らし・消費・教育: 3〜5件
- 文化・エンタメ・趣味: 3〜5件
- ネット文化・ミーム: 0〜3件。質の高い候補がない日は0件でよい
- スポーツ: 1〜3件
- 地域・人物・意外性のある話題: 2〜4件
- VCF・VMware・競合: 一般枠とは別に0〜5件。新情報がない日は古い記事で埋めない

一般ニュースではテクノロジーとセキュリティを合計して全体の40％を超えない。VCF専門枠は件数計算から外し、一般ニュースの分野バランスを崩さない。

AIと一般脆弱性の横断監視は、重要候補を発見し損ねないために行う。監視対象という理由だけで一般ニュースの採用枠を予約せず、採用時は一般ニュースと同じ重要性、話題性、多様性、重複除外、40％上限を適用する。VCF専門枠は仕事上の監視であり、一般ニュースの件数、分野比率、Top 5から完全に分離する。

## VCF専門枠

毎日、次の情報群を並行して確認する。単一のブログ一覧だけで巡回完了としない。

- Broadcom／VMware公式ブログ、TechDocs、製品別リリースノート、Knowledge Base、Security Advisory
- Broadcom Support PortalのVCF区分とApplication Networking and Security区分の両方
- Broadcom Service Status、緊急障害、パッチの撤回・再公開、アップグレード停止推奨
- Product Interoperability Matrix、Compatibility Guide、Hardware Compatibility List、サポート終了・ライフサイクル表
- ライセンス、価格、サポート、パートナー、VCSP制度の変更
- William LamのブログとX、Duncan EppingのYellow BricksとX
- Cormac Hogan、Frank Denneman、Niels Hagoort、Bob Plankers、Pete Flecha、Eric Sloof、Chris Wahl、Viktor van den Bergなど、実機検証を公開するエンジニア
- Broadcom Community、VMware {code}、vExpert、Redditなどの運用者コミュニティ
- Veeam、NVIDIA、Dell、HPE、NetAppなど、バックアップ、GPU、サーバー、ストレージの主要連携ベンダー
- Nutanix、Hyper-V／Azure Stack HCI、Proxmox、OpenShift Virtualizationなど、競合・移行先の重要な製品変更

個人ブログやXは、公式資料だけでは分かりにくい制約、実機検証、回避策、アップグレード時の注意を見つける入口として重視する。ただし、製品仕様、対応バージョン、脆弱性、ライセンス、サポート可否はBroadcom公式文書でも照合する。「公式確認済みの事実」「個人の検証結果」「推測・意見」を明確に分け、個人投稿を一般的事実の唯一の根拠にしない。

対象はVCF、vSphere、ESXi、vCenter、vSAN、NSX、HCX、VCF Operations、VCF Automation、Tanzu／VKS、vDefend Firewall、vDefend Security Services Platform（SSP）、Avi Load BalancerのController・Service Engine・Avi Operations・WAF・GSLB、VCSP、ライセンス・サポート・パートナー制度とする。各記事では対象製品とバージョン、影響を受ける利用者、運用上の意味、既知の制約、公式根拠、次に確認すべき点を示す。特に脆弱性、データ損失、停止、検知・フロー・監査情報の欠落、互換性喪失、サポート終了、パッチ撤回、アップグレード停止推奨を通常の機能紹介より優先する。該当する新情報がない日は0件とし、古い記事や軽微な更新で枠を埋めない。

AviとvDefendは製品別KB、リリースノート、VMSA、既知障害を毎日独立確認する。VCF Operationsで最新VMSAが表示されない問題、vDefendでフローや検知データが欠落する問題、Aviが背後サービスへ提供するWAF緩和策も運用影響があれば候補とする。ただし「Avi自体は非該当だが背後を保護できる」のような情報を、Avi自体の脆弱性と誤記しない。

巡回先がログイン要求、削除、アクセス制限、障害などで確認できない場合は、確認済みと扱わない。制限を回避せず、取得不能であることを編集記録へ残し、同じ内容を公式文書や別の信頼できる公開情報から確認する。X、Reddit、コミュニティ投稿の反響を一般利用者全体の評価とは表現しない。

同じ出来事について、公式情報と現場検証の両方に価値がある場合は、原則として一つの記事に統合して両方のURLと立場を説明する。仕様とサポート可否は公式情報を優先し、個人検証は再現条件、対象バージョン、未検証範囲を明示する。

同一媒体は原則4件まで、同一組織の公式発表は原則3件までとする。同じ出来事を扱う記事は、独自情報や明確に異なる視点がない限り重複掲載しない。

## Top 5の選び方

Top 5は「最も硬い5件」でも「人気指標の上位5件」でもない。次の観点を組み合わせ、その日の全体像が5件で伝わるように選ぶ。

1. 多くの人の生活、安全、権利に関係するもの
2. 国内外の大きな変化を理解するために必要なもの
3. はてなブックマーク、Hacker News、Togetter、Redditなどで実際に議論が広がったもの
4. 専門外でも知る価値がある科学、文化、教育、スポーツ、地域、ネット文化などのもの
5. 驚き、発見、人間味、前向きな変化のあるもの

Top 5は4分野以上、4媒体以上から選ぶ。テクノロジー・セキュリティ・VCF系は合計2件まで、政府機関などの公式発表は合計2件までとする。Hacker News、はてなブックマーク、またはソーシャル発見由来を合計2件以上含め、文化、暮らし、科学、スポーツ、地域・人物、ネット文化のいずれかから1件以上含める。ミームや流行動画も、発祥・素材・拡散を十分に検証でき、当日の文化的な動きを理解する価値があればTop 5に選べる。国や地域を理由にTop 5へ入れたり外したりしない。4chan由来の記事をTop 5に入れる場合は、一次資料または複数の信頼できる報道による裏付けを必須とする。

## 人気指標の扱い

- はてなブックマーク数、Hacker Newsのポイント数・コメント数は、確認した時刻とともに記録する。
- Togetterの閲覧数、Redditのスコア・コメント数、4chanの返信数など、取得可能なソーシャル指標も確認時刻とともに記録する。
- 数値は変動するため、順位の絶対的な根拠にはしない。
- 扇情的、差別的、誤情報の疑いがある記事は、人気が高くても採用しない。
- 意見記事は事実報道と区別し、反対意見や一次資料を確認する。
- Hacker Newsでは技術記事だけに偏らず、科学、教育、経済、公共政策、歴史、文化、個人プロジェクトも候補にする。
- はてなブックマークでは政治・炎上だけに偏らず、生活、仕事、創作、趣味、地域の話題も候補にする。
- GIGAZINEなどの横断媒体は幅を広げる入口に使い、海外記事では元の報道、論文、公式発表まで遡る。

## 選定手順

1. 前日から当日朝までを基本対象期間として、Hacker News、はてなブックマーク、Reddit、4chan、Lobsters、Togetter、TikTok、YouTube、Instagram Reels、ニコニコ、Bluesky、Mastodon、GIGAZINE、一般報道・一次情報から並行して候補を集める。
2. URL、公開日、出典、情報種別、人気指標を確認する。未来日付、架空URL、検索結果だけの情報は採用しない。
3. 重複を除き、分野、媒体、地域、硬軟、専門内外の偏りを確認する。
4. 質と多様性を満たす記事を選び、件数調整のための水増しや機械的な削除を行わず、最後にTop 5を別工程で選ぶ。
5. 独自タイトル、結論・主要事実・適用範囲の3段落かつ合計240文字以上の自己完結した概要、300文字以上の独自解説、構造化した詳細欄、注目理由、確認できた範囲の現在の反響、中立的な反響評価を作成し、編集・権利ポリシーに従って確認する。
6. 概要、解説、注目理由、反響評価の重複と、記事固有の理解を増やさない定型句がないことを確認する。結論が最後まで分からない構成、固有名詞の羅列、注意書きだけで終わる解説は差し戻す。
7. データ検証、テスト、ビルド後に公開する。

## 採用しない選び方

- URLを検証しやすいという理由だけで官公庁発表を大量採用する
- 一つの媒体からまとめて取得して件数を満たす
- 編集者の専門分野だけで一般ニュースの大半を構成する
- 30件へ合わせるため、重要性や検証材料の乏しい記事を採用する
- 30件を超えたという理由だけで、重要かつ重複しない記事を除外する
- カテゴリ名だけを「生活・文化」にして、実質的な硬さや偏りを隠す
- 人気指標だけで真偽や重要性を判断する
- 架空の記事、将来の出来事、確認できない数値を実在ニュースとして扱う
