# Muse レビュー（外部監査）

このフォルダは、Codex が生成・公開した毎日のニュースまとめに対する、Muse（外部監査役）による日次レビューの置き場です。

## 目的

- 生成ルール `automation/daily-news-digest.prompt.md` をすり抜けた問題（概要・背景の説明不足、用語説明のない記述、価値のない定型解説、欄同士の重複など）を、公開後に第三者の目で検出する。
- 検出だけで終わらせず、プロンプトとバリデータへの具体的な強化案まで記録し、再発を機械的に止められる状態へ近づける。

## ファイル

- `YYYY-MM-DD.md`：その日付版（`data/daily/YYYY-MM-DD.json`）に対するレビュー。公開後に1日1ファイル。
- このファイル（`README.md`）：運用ルールと書式の定義。

## レビューの書式

各レビューは次の構成とする。

1. **対象と総合評価**：対象版、記事数、総合所見（重大な指摘の件数を含む）。
2. **機械チェック結果**：件数、文字数、定型文（埋め草）の出現数、欄同士の重複率など、再現可能な数値。
3. **指摘**：深刻度（重大／中／軽）ごとに、記事ID、問題の文の引用、違反しているルールの要点を記す。推測ではなく、データから確認できたことだけを書く。
4. **良かった点**：ルールどおりに書けている記事・欄を具体的に挙げる。
5. **強化案**：バリデータ（`src/lib/schema.ts`、`scripts/`、`tests/`）とプロンプトへの提案。実装はこのフォルダでは行わず、提案として記録する。
6. **前回指摘の再発チェック**（2回目以降）：前回までの指摘が再発したか、改善したかを記す。

## Codex へのお願い（読み手としての使い方）

- 次回版の生成前に、最新のレビューを読み、指摘されたパターンを繰り返さないこと。
- レビュー内の文面を、そのまま記事へ転記しないこと（レビューは監査記録であり、記事の材料ではない）。
- 強化案の採否は人間（リポジトリ管理者）が判断する。レビューが入ったこと自体を公開版の正しさの根拠にしないこと。

## 運用

- レビューは Muse が毎日、公開後に作成してこのフォルダへ登録する。要約は管理者へチャットでも届ける。
- レビューは公開済み記事を書き換えるものではない。記事の修正判断は管理者が行う。

## Issue 連携の運用

- レビュー登録と同日に、日次 Issue を1件立てる。タイトルは `[Museレビュー] YYYY-MM-DD版：重大X件（主な指摘の要約）` とする。
- Issue 本文には、総合評価、重大な指摘の要約、強化案の対応チェックリスト、レビューファイル（`reviews/YYYY-MM-DD.md`）へのリンクを載せる。
- 前日以前の Muse レビュー Issue で、今回改善が確認できた項目があれば、その Issue に改善確認のコメントを残す。
