# 執筆工程

読むタイミング: 各記事を執筆・検証・凍結するとき。共通核`automation/daily-news-digest.prompt.md`と併せて読む。

## 全記事の編集基準

想定読者はソフトウェア、インフラ、AI、セキュリティの基礎があるエンジニア本人である。初学者向けの「XとはYです」を避け、既知の概念へ短く接続してから、今回固有の構造、障害モード、規模、費用、運用判断を説明する。専門外の科学、経済、制度、個別業界は具体例と数値比較で橋渡しする。

### 素材を先に確定して書く

本文は、各記事の一次資料から採った固有素材を変形して作る。確定台帳の該当行と一次資料を読み、書き始める前に`generated/articles/YYYY-MM-DD/anchors/<article-id>.json`へ、根拠URLとともに次を記録する。

- 出来事を特定する数値、固有名詞、日付・時点、対象範囲。
- 何がどの順で起きる仕組み、または因果の段階。
- 影響を受ける主体と、その影響が生じる条件・境界。
- 未確定の事項（期限、続報、未公表の見解、確定していない数値など）。根拠のある説明の対立があれば両方。

これは列挙用のメモではなく、各欄で使う材料である。一次資料からこれらを十分に採れない候補は、本文を書かず選定工程へ戻す。数値・固有名詞・日付だけのアンカーで完了とせず、仕組み、影響条件、未確定事項を確認してから本文へ進む。選んだ記事の`articleDetail.facts`が空なら素材抽出の失敗として同じ手順へ戻る。ほかの詳細欄は該当する素材だけを置くが、一般論や監視予定で埋めない。題材別プレイブック（`docs/topic-editorial-playbooks.md`）に該当する記事は、その節が指定する素材もアンカーに集める。一次資料が開示していない素材はアンカーに未公表と記録し、本文では未公表であることを事実として書く。一般的な助言は素材の代替にならない。

### 素材から欄ごとに組み立てる

- `summary`は、結論・主要事実・適用範囲を3段落、合計240文字以上で組み立てる。第1段落は、主体、出来事、変化をその記事の固有名詞で示す。
- `comment`は、アンカーの複数の点を実際に使い、出来事の仕組みまたは因果と、対象者への影響・条件をつなげて説明する。数値、固有名詞、日付・時点は材料にある限り本文で確認できる形にする。Top 5は背景・仕組み・比較・影響・判断軸を素材の関係として展開し、独自の見立て・評価・見通し（追加観点）はここだけに置く。非Top 5は事実の位置づけと理解に必要な背景事実を中立的に補足し、独自の見立て・評価・見通し・推奨は加えない。
- `articleDetail`はアンカーの整理である。`facts`には出来事そのもの、`background`には前提、`explanation`には仕組み・因果、`implications`には影響を受ける主体と条件、`caveats`には根拠の限界または対立する説明、`nextChecks`には未確定事項を置く。結論以外の同じ素材を複数欄で言い換えて重ねない。
- `attentionAnalysis.whyNotable`は、「誰の、どの判断・運用が、どの条件または期限で変わるか」を、アンカーにある主体・条件・時点で書く。`currentReaction`は従来どおり実測値と確認時刻に基づける。`assessmentComment`も、反応の範囲と記事固有の素材を結んで評価理由を示す。
- `articleDetail.nextChecks`は、次に何が起きれば判断が更新されるかを、その記事の未確定事項、期限、発表主体で具体化する。

字数下限は、Top 5の`comment`が300文字以上、非Top 5の`comment`が150文字以上、概要が240文字以上とする。足りないときは文を足さず一次資料へ戻り、使える固有素材とその関係を増やしてから欄を組み直す。全記事の上限は1000文字である。

同じ文や型を量産するのではなく、採用した各記事のアンカーから個別に文を作る。編集本文を生成スクリプトで作ってはいけない。スクリプトは候補取得、メタデータ整理、重複検出、検証、音声処理に限る。

### 表現と根拠の基準

- 独自タイトルを付ける。概要、解説、詳細、注目理由、台本で同じ文や結論を再掲しない。結論の正本だけは概要第1段落、`articleDetail.conclusion`、台本冒頭の概要で共有できる。
- 数字には母数、期間、定義、比較対象を付ける。研究は対象数、方法、相関と因果、査読状況を確認する。
- 主張を事実、当事者説明、解釈、推定、予測に分け、一次資料と独立資料で照合する。根拠のある別解釈があれば重み付きで示し、偽のバランスは作らない。
- 「なぜ今起きたか」を調べ、公式理由、報道分析、編集上の推論を分ける。
- 具体情報を増やさない留保、編集手順、監視予定、意味のない三項目以上の列挙を削除する。
- 前日7時より前の記事は`lateInclusion`を付ける。既掲載事案は実質更新または明確な再燃がある場合だけ`followUp`と`relatedArticleIds`を付け、元掲載日と変化を冒頭で示す。「再確認：」は使わない。
- `publishedAt`は一次資料の表示時刻をそのまま使い、丸めたりフィードの取り込み時刻で代用したりしない。

### 1記事を凍結する完了ゲート

採用記事は必ず1件ずつ完結させる。通常、復旧、差し戻しのいずれでも、次の記事へ進む前に次を順番に終える。(1)確定台帳の該当行と一次資料だけを開く。(2)上記の固有素材をアンカー事実として保存する。アンカーファイルが存在しない、または`facts`に置ける出来事の素材がない記事は未完了である。(3)`summary`、`articleDetail`、`comment`、`attentionAnalysis`の順に、各欄をアンカーから組み立てる。本文中に新しい英字固有名詞・製品名・ライブラリ名・略語が出た時点で、公式または信頼できる読みを確認して`config/pronunciations.json`へ登録する。(4)本文のsummary第1段落と`articleDetail.conclusion`から、その記事固有の見出しを最後に付ける。仮置きの「本日の更新」などの見出しで記事ファイルを保存せず、仮置き見出しのまま単体検証へ進まない。(5)完成した版JSONの記事オブジェクトそのものを`generated/articles/YYYY-MM-DD/<article-id>.json`へ保存する。(6)まず`articleSchema`による単体検証、続けて`npm run edition:guard -- --single generated/articles/YYYY-MM-DD/<article-id>.json`を通す。(7)独立した記事単位監査で、`comment`、`whyNotable`、`nextChecks`の各文がどのアンカー素材に対応するかを確認する。対応のない文は表現を足す対象ではなく素材不足として抽出工程へ差し戻す。数値・固有名詞・題材の一致も確認する。題材別プレイブックに該当する記事では、監査に該当節も渡し、節が指定する素材が本文で使われているか、未公表として記録されているかも確認する。指定素材が助言や留保で置き換えられている記事は未完了として差し戻す。(8)Top 5の記事では、英語学習用に英語版（`englishVersion`のtitle・summary・comment）も作る。完成した日本語本文を文単位で訳すのではなく、アンカー素材と一次資料から英語で組み立てる。数値・固有名詞・版番号・日時は日本語版と一致させ、summaryの段落構成も日本語版にそろえて対で読める形にする。英語版も日本語版と同じ編集基準で書き、具体情報を増やさない留保だけで埋めない。記事単位監査では英語版についても、数値と固有名詞のアンカー対応と、日本語版にない内容が混ざっていないかを確認する。

アンカー保存、素材を使った本文、本文から付けた見出し、両方の単体検証、記事単位監査のすべてが通過するまで記事を凍結しない。Top 5は台本と英語版を保存後に同じ単体検証と監査を再実行し、通過した記事だけを台本と英語版を含めて凍結する。修正が必要なら該当記事ファイルだけを直す。一括執筆や一括復旧で完了ゲートを後回しにしない。

版JSONを主担当が直接編集してはいけない。すべての記事が凍結された後、`npm run edition:assemble -- --date YYYY-MM-DD`の生成物だけを`data/daily/YYYY-MM-DD.json`とする。これは本文生成ではなく結合であり、日付別の本文生成スクリプトを作って全件再生成する禁止を回避するものではない。18件以上で品質を維持できない候補しか残らなければ、短縮理由を記録して完成工程へ進む。

企業・雇用、制度・規制、ボット判定、科学、AIモデル・製品世代、セキュリティ事故などに該当する記事だけ、`docs/topic-editorial-playbooks.md`の該当節を読む。すべての専門ルールを毎回読み込まない。

コメント欄やソーシャル反応は追加検証の入口に使い、事実や一般世論の根拠にしない。反響値は実測値と確認時刻を記事・サイト・RSSに残すが、音声では「今朝の時点で」と簡潔にする。値がなければ編集手順を読み上げず、記事概要へ直接進む。
