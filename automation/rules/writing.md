# 執筆工程

読むタイミング: 各記事を執筆・検証・凍結するとき。共通核`automation/daily-news-digest.prompt.md`と併せて読む。

## 全記事の編集基準

想定読者はソフトウェア、インフラ、AI、セキュリティの基礎があるエンジニア本人である。初学者向けの「XとはYです」を避け、既知の概念へ短く接続してから、今回固有の構造、障害モード、規模、費用、運用判断を説明する。専門外の科学、経済、制度、個別業界は具体例と数値比較で橋渡しする。

各記事は次を満たす。

- 独自タイトル。概要は結論・主要事実・適用範囲の3段落、合計240文字以上。第1段落だけで誰が何をして何が変わったか分かる。
- Top 5の`comment`は300文字以上。概要を言い換えず、背景、仕組み、比較、影響、判断軸を含む詳細な解説とし、独自の見立て・評価・見通し（追加観点）はここだけに書く。
- 非Top 5の`comment`は150文字以上の「中立的な分析と補足」とし、事実の位置づけ、理解に必要な背景事実、一次資料に基づく補足だけを書く。独自の見立て・評価・見通し・推奨は書かない。全記事の上限は1000文字。
- `attentionAnalysis`（注目理由と影響）と`articleDetail`（事実に基づく詳細・補足）はTop 5かどうかにかかわらず全記事で維持する。`articleDetail`は具体情報がある欄だけ使い、情報がなければ空配列とし、一般論や監視予定で埋めない。
- 数字には母数、期間、定義、比較対象を付ける。研究は対象数、方法、相関と因果、査読状況を確認する。
- 主張を事実、当事者説明、解釈、推定、予測に分け、一次資料と独立資料で照合する。根拠のある別解釈があれば重み付きで示し、偽のバランスは作らない。
- 「なぜ今起きたか」を調べ、公式理由、報道分析、編集上の推論を分ける。
- 概要、解説、詳細、注目理由、台本で同じ文や結論を再掲しない。結論の正本だけは概要第1段落、`articleDetail.conclusion`、台本冒頭の概要で共有できる。
- 具体情報を増やさない留保、編集手順、監視予定、意味のない三項目以上の列挙を削除する。
- 前日7時より前の記事は`lateInclusion`を付ける。既掲載事案は実質更新または明確な再燃がある場合だけ`followUp`と`relatedArticleIds`を付け、元掲載日と変化を冒頭で示す。「再確認：」は使わない。
- `publishedAt`は一次資料の表示時刻をそのまま使い、丸めたりフィードの取り込み時刻で代用したりしない。

記事本文、`summary`、`comment`、`articleDetail`、台本を、ループ、共通テンプレート、文字列置換、`.repeat()`、記事名だけを差し替える生成スクリプトで作ってはいけない。スクリプトへ任せるのは候補取得、メタデータ整理、重複検出、検証、音声処理だけとし、編集本文は採用した各記事の根拠メモから個別に書く。

採用記事は必ず1件ずつ完結させる。次の完了ゲートを通してから次の記事へ進む。(1)確定台帳の該当行と一次資料だけを開く。(2)数値、固有名詞、日付を`generated/articles/YYYY-MM-DD/anchors/<article-id>.json`へアンカー事実として保存する。アンカーファイルが存在しない記事は未完了である。(3)`summary`、`articleDetail`、`comment`の順に本文を書く。本文中に新しい英字固有名詞・製品名・ライブラリ名・略語が出た時点で、公式または信頼できる読みを確認して`config/pronunciations.json`へ登録する。(4)本文のsummary第1段落と`articleDetail.conclusion`から、その記事固有の見出しを最後に付ける。仮置きの「本日の更新」などの見出しで記事ファイルを保存せず、仮置き見出しのまま単体検証へ進まない。(5)完成した版JSONの記事オブジェクトそのものを`generated/articles/YYYY-MM-DD/<article-id>.json`へ保存する。(6)まず`articleSchema`による単体検証、続けて`npm run edition:guard -- --single generated/articles/YYYY-MM-DD/<article-id>.json`を通す。(7)独立した記事単位監査でアンカーと数値・固有名詞・題材の一致を確認する。アンカー保存、本文、本文から付けた見出し、両方の単体検証、記事単位監査のすべてが通過するまで次の記事に進まない。Top 5は台本を保存後に同じ単体検証と監査を再実行し、通過した記事だけを台本を含めて凍結する。修正が必要なら該当記事ファイルだけを直す。

版JSONを主担当が直接編集してはいけない。すべての記事が凍結された後、`npm run edition:assemble -- --date YYYY-MM-DD`の生成物だけを`data/daily/YYYY-MM-DD.json`とする。これは本文生成ではなく結合であり、日付別の本文生成スクリプトを作って全件再生成する禁止を回避するものではない。18件以上で品質を維持できない候補しか残らなければ、短縮理由を記録して完成工程へ進む。

企業・雇用、制度・規制、ボット判定、科学、AIモデル・製品世代、セキュリティ事故などに該当する記事だけ、`docs/topic-editorial-playbooks.md`の該当節を読む。すべての専門ルールを毎回読み込まない。

コメント欄やソーシャル反応は追加検証の入口に使い、事実や一般世論の根拠にしない。反響値は実測値と確認時刻を記事・サイト・RSSに残すが、音声では「今朝の時点で」と簡潔にする。値がなければ編集手順を読み上げず、記事概要へ直接進む。
