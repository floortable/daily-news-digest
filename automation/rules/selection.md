# 選定工程

読むタイミング: 候補の収集、分類、横断監視を行うとき。共通核`automation/daily-news-digest.prompt.md`と併せて読む。

## 候補台帳を先に完成させる

最初に`npm run candidates:collect -- --date YYYY-MM-DD`を実行し、上限45件へ圧縮された`generated/candidates/YYYY-MM-DD.json`を候補台帳の土台にする。失敗したフィードだけブラウザーで代替確認する。`config/monitoring-sources.json`の必須巡回先、前日版の続報候補、Hacker News、はてなブックマーク、一般報道、ソーシャル発見を一巡し、候補ごとに見出し、URL、公開日時、出来事、一次資料、話題性、重複先、暫定採否を1行で記録する。

重要候補を`included`、`deferred`、`not-relevant`へ分類したら、収集出力とは別の確定台帳`generated/candidates/YYYY-MM-DD.final.json`へ全候補を保存する。collectorの出力を土台にしつつ、巡回で追加した候補も台帳に加え、全候補の`decision`を記録する。`included`にはこの時点で一意な`articleId`を記録する。collectorを再実行しても分類結果を失わないよう、`.json`と`.final.json`は混同しない。

確定台帳を保存したら、本文の前に選定直後の漏れチェックを一度だけ行う。`config/monitoring-sources.json`の監視定義ソース、AI各社、CISA KEV、NVD、JPCERT/CC、CERT/CC、VCF各経路と台帳を突き合わせ、漏れを候補として台帳へ追加・分類して確定台帳を更新する。この突き合わせと確定台帳保存が済むまで本文に着手しない。必須巡回後の一般検索は不足分を補う一巡に限定し、同じ検索語の言い換えを繰り返さない。候補固定後の検索は採用記事の事実確認、背景、比較、反響の裏付けだけに使う。

個別の記事URLがHTTP 403、429、タイムアウト、robots制限、ブラウザー取得不能になっても、それはその候補・取得経路だけの制約であり、日次版全体の公開停止条件ではありません。同じURLの再試行は1回までとし、候補台帳の`sourceSummary`と`discoveryUrl`を発見材料に、(1)企業・機関・研究者の一次資料、(2)同じ発表の配信資料・公式文書・機械可読フィード、(3)別の信頼できる報道、の順で限定的に代替確認する。RSS要約やコメントだけを中心事実の根拠にはしません。中心事実を確認できなければその候補だけを`deferred`または`not-relevant`へ移し、候補台帳から別記事へ差し替える。非Top 5の取得不能、特定媒体の一括403、一般検索ツールの失敗、候補ページ数件の検証失敗を、版全体の事実確認不能へ拡大してはいけません。

復旧は「代替経路を1巡→候補差し替え→記事数を18件、なお必要なら15件まで縮小」の順で行う。Top 5の候補が取得不能なら、構成条件を満たす別候補へ入れ替え、5件すべての中心事実を確認できるまで続ける。公開停止を判断できるのは、候補台帳の高重要度候補を分類し、代替経路と差し替え候補を実際に試し、15件以上の根拠ある一般記事または構成条件を満たすTop 5を作れない結果が残った場合だけです。403の件数や取得不能な媒体名だけでは停止根拠になりません。

一般ニュースは通常25〜35件、30件前後とするが、弱い記事や検証不能な記事で埋めない。18件以上の高品質な記事を完成できた後は、件数を満たすために定型文へ落とさず、残る候補の固有情報が不足する場合は18〜24件で公開する。レビュー修正で記事を外して18件を下回った場合も、Top 5を含む15件以上に固有の根拠があれば公開を優先し、探索数と除外理由を`selectionShortfallReason`へ具体的に書く。25件未満なら候補台帳と`monitoringReview.findings`を照合し、高重要度の未分類、見落とし、一次資料を取得できる候補が残っていないことを確認する。

分野と媒体の詳細基準は`docs/selection-policy.md`、巡回記録は`docs/monitoring-policy.md`に従う。一般ニュースのテクノロジーとセキュリティは合計40％を目安とし、8件未満の短縮版では60％を目安とする。これは多様性を保つ選定バランスの指針であり、重要度の高いニュースを落とす理由にはしない。拾い漏れチェックや監視で重要と判断した、広く使われる製品・サービスの脆弱性、CISA KEV掲載、情報漏えい・不正アクセス、VCF関連、重要なAI発表などは、目安を超えても採用する。超過時は、採用記事と重要と判断した理由を`selectionShortfallReason`または該当する`findings`の注記に記録する。同一媒体は原則4件以下。VCF専門枠は一般枠と分離して0〜5件とし、新情報がなければ0件にする。

Top 5は5件、4分野以上、4媒体以上から選ぶ。技術・セキュリティは2件以下、政府公式発表は2件以下、Hacker News・はてな・ソーシャル由来を2件以上、文化・暮らし・科学・スポーツ・地域・人物・ネット文化から1件以上含める。個人リスナーは野球に関心がないため、競技結果や移籍などの野球記事をTop 5へ通常採用しない。

## 4. 横断監視

AIはOpenAI、Anthropic、Google／DeepMind、Microsoft、Meta、NVIDIAのモデル、API、安全性、障害、買収、サービス終了、価格・条件変更を確認する。セキュリティはCISA KEVのJSON、JVN／JPCERT、主要プロジェクト・ベンダー告知、公開調査フィードを一般検索より先に確認する。悪用確認、認証前RCE、サプライチェーン侵害は不採用でも`findings`へ理由を残す。軽微なCVEやベンチマーク順位だけで一般枠を埋めない。

VCFは`config/monitoring-sources.json`の項目を確認する。公式製品発表は独立経路とし、新版、ライセンス、製品追加・終了・改名、販売・サポート期限、地域・購入条件の変更も、セキュリティ情報でなくてもfindingsとして必ず評価し、理由を記録する。サイバーセキュリティ戦略本部の新会合・決定、国家サイバー統括室の報道発表、IPAの統一基準・行動計画・基本方針・対策パッケージ・ガイドライン・制度変更等の政策公表は、インフラ運用に一括対応を要するため、findingsとして必ず評価する。運用対応が必要なら記事化候補とし、期間前の未掲載の重要な製品発表・決定・要請は`lateInclusion`として再評価する。評価では会合・決定、対象（重要インフラ事業者、政府機関、一般企業等）、期限、仮想化基盤運用の変更を押さえる。William Lam、Duncan Epping、運用者コミュニティの情報は公式資料で照合する。取得不能は`restricted`/`failed`として実態、時刻、URLを個別記録し、注記を全件へコピーしない。

ミーム・流行動画は0〜3件を目安とし、発祥、元素材、音源、拡散経路、広告・仕込み、権利を確認できたものだけ扱う。元動画、画像、音源、歌詞、サムネイルは転載せず、二次被害のおそれがある題材は採用しない。
