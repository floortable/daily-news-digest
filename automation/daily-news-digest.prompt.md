# 毎日の注目記事約30選＋VCF運用監視

改訂: 2026-11-10。本文を記事単位で凍結し、確定台帳と個別記事から版JSONを決定的に結合する工程へ変更した。

毎日7時（Asia/Tokyo）、当日版の記事、Top 5音声、RSS、サイトを完全自動で更新する。作業対象はリポジトリのルートとし、有料API、従量課金サービス、追加課金は使わない。動画とBGMなし版は生成しない。

## 1. 開始と既知問題

安全に最新の`main`へ同期し、作業ツリーにある利用者の変更を保護する。`reviews/README.md`と最新の`reviews/YYYY-MM-DD.md`を読む。レビューの入力はVM生成の`reviews/`だけとし、廃止済みのGitHub Issue確認やMac生成は行わない。外部レビューを取得できないことだけを理由に生成を停止せず、公開前の独立編集レビューを修正工程として使う。

レビューは再発防止に使うが、指摘を鵜呑みにせず、現行データ、一次資料、検査コードで再現する。レビューの文章、数値、評価をニュースの事実や記事材料として転記してはいけません。レビューや監査の存在を公開版の正しさの根拠にしない。強化案は誤検知と運用負担を評価し、再現可能なものだけ恒久対策にする。Issue運用は廃止済みであり、Issueの作成・更新・クローズは行わない。

## 2. モデルとコンテキスト

毎回新しい独立ジョブを`model: "gpt-5.6-terra"`、`reasoning_effort: "medium"`で実行する。過去の実行チャットを継承せず、現行ファイルを正本とする。調査、選定、執筆、修正、公開は主担当1体が順番に行い、これらのためにサブエージェントを起動しません。定型確認、候補整理、重複検査、検証、音声処理はスクリプトへ任せ、成功ログや一覧をモデルへ再掲しない。

サブエージェントは、記事単位の独立監査と公開前の版全体独立編集レビューにだけ使う。主担当で使えるモデル名とサブエージェントへ指定できるモデル名は別に扱い、各監査を`fork_turns: "none"`、`model: "gpt-6-sol"`、`reasoning_effort: "low"`で起動する。記事単位監査へは対象記事の台帳行、一次資料、アンカーだけを、版全体レビューへは`docs/editorial-audit-rubric.md`と生成済み監査バンドルだけを渡す。最新レビューや主担当の評価を渡さず、記事本文やログ全文をルートへ再掲させません。版全体レビューは1回だけとし、合否判定や公開停止権を持たせない。主担当は指摘を修正リストとして処理し、根拠不足の非Top 5は削除または確認できる候補へ差し替え、Top 5の中心事実を確認できなければ候補台帳から別記事へ入れ替える。修正後は機械検査と主担当の差分確認を行い、版全体レビューを再依頼しない。レビューの指摘件数や表現上の問題だけを理由に公開を止めてはいけません。指定モデルが利用不能な場合は該当レビューを省略し、主担当の最終一巡と機械検査を強化して完走する。

コンテキストへ全候補、全データ、全スキーマ、全ツール定義を表示しない。既知のツールを探すためにツール一覧を列挙せず、候補は必要な列だけ40件以下、ファイルは必要な範囲だけ取得し、1回の出力を原則8,000文字以下にする。同じ検証コマンドを修正なしで繰り返さない。

本文の執筆・記事単位監査でコンテキストに置くのは、対象記事の確定台帳行、一次資料、アンカー事実だけとする。他記事の本文や版JSON全体を開かない。記事単位監査も上記の独立編集レビュー規定と同じく、執筆とは独立した文脈、`fork_turns: "none"`、`model: "gpt-6-sol"`、`reasoning_effort: "low"`で1記事ずつ行う。ただし版全体の公開前レビュー1回とは別に、各記事の執筆直後に行い、記事の台帳行・一次資料・アンカーだけを渡す。

## 3. 候補台帳を先に完成させる

最初に`npm run candidates:collect -- --date YYYY-MM-DD`を実行し、上限45件へ圧縮された`generated/candidates/YYYY-MM-DD.json`を候補台帳の土台にする。失敗したフィードだけブラウザーで代替確認する。`config/monitoring-sources.json`の必須巡回先、前日版の続報候補、Hacker News、はてなブックマーク、一般報道、ソーシャル発見を一巡し、候補ごとに見出し、URL、公開日時、出来事、一次資料、話題性、重複先、暫定採否を1行で記録する。

重要候補を`included`、`deferred`、`not-relevant`へ分類したら、収集出力とは別の確定台帳`generated/candidates/YYYY-MM-DD.final.json`へ全候補を保存する。collectorの出力を土台にしつつ、巡回で追加した候補も台帳に加え、全候補の`decision`を記録する。`included`にはこの時点で一意な`articleId`を記録する。collectorを再実行しても分類結果を失わないよう、`.json`と`.final.json`は混同しない。

確定台帳を保存したら、本文の前に選定直後の漏れチェックを一度だけ行う。`config/monitoring-sources.json`の監視定義ソース、AI各社、CISA KEV、NVD、JPCERT/CC、CERT/CC、VCF各経路と台帳を突き合わせ、漏れを候補として台帳へ追加・分類して確定台帳を更新する。この突き合わせと確定台帳保存が済むまで本文に着手しない。必須巡回後の一般検索は不足分を補う一巡に限定し、同じ検索語の言い換えを繰り返さない。候補固定後の検索は採用記事の事実確認、背景、比較、反響の裏付けだけに使う。

個別の記事URLがHTTP 403、429、タイムアウト、robots制限、ブラウザー取得不能になっても、それはその候補・取得経路だけの制約であり、日次版全体の公開停止条件ではありません。同じURLの再試行は1回までとし、候補台帳の`sourceSummary`と`discoveryUrl`を発見材料に、(1)企業・機関・研究者の一次資料、(2)同じ発表の配信資料・公式文書・機械可読フィード、(3)別の信頼できる報道、の順で限定的に代替確認する。RSS要約やコメントだけを中心事実の根拠にはしません。中心事実を確認できなければその候補だけを`deferred`または`not-relevant`へ移し、候補台帳から別記事へ差し替える。非Top 5の取得不能、特定媒体の一括403、一般検索ツールの失敗、候補ページ数件の検証失敗を、版全体の事実確認不能へ拡大してはいけません。

復旧は「代替経路を1巡→候補差し替え→記事数を18件、なお必要なら15件まで縮小」の順で行う。Top 5の候補が取得不能なら、構成条件を満たす別候補へ入れ替え、5件すべての中心事実を確認できるまで続ける。公開停止を判断できるのは、候補台帳の高重要度候補を分類し、代替経路と差し替え候補を実際に試し、15件以上の根拠ある一般記事または構成条件を満たすTop 5を作れない結果が残った場合だけです。403の件数や取得不能な媒体名だけでは停止根拠になりません。

一般ニュースは通常25〜35件、30件前後とするが、弱い記事や検証不能な記事で埋めない。18件以上の高品質な記事を完成できた後は、件数を満たすために定型文へ落とさず、残る候補の固有情報が不足する場合は18〜24件で公開する。レビュー修正で記事を外して18件を下回った場合も、Top 5を含む15件以上に固有の根拠があれば公開を優先し、探索数と除外理由を`selectionShortfallReason`へ具体的に書く。25件未満なら候補台帳と`monitoringReview.findings`を照合し、高重要度の未分類、見落とし、一次資料を取得できる候補が残っていないことを確認する。

分野と媒体の詳細基準は`docs/selection-policy.md`、巡回記録は`docs/monitoring-policy.md`に従う。一般ニュースのテクノロジーとセキュリティは合計40％以下。ただし一般ニュースが8件未満の短縮版だけは60％以下とする。短縮版は例外的な編成で1件の増減が比率を大きく動かすためであり、件数が8件へ戻れば多様性を守る40％上限を再び適用する。同一媒体は原則4件以下。VCF専門枠は一般枠と分離して0〜5件とし、新情報がなければ0件にする。

Top 5は5件、4分野以上、4媒体以上から選ぶ。技術・セキュリティは2件以下、政府公式発表は2件以下、Hacker News・はてな・ソーシャル由来を2件以上、文化・暮らし・科学・スポーツ・地域・人物・ネット文化から1件以上含める。個人リスナーは野球に関心がないため、競技結果や移籍などの野球記事をTop 5へ通常採用しない。

## 4. 横断監視

AIはOpenAI、Anthropic、Google／DeepMind、Microsoft、Meta、NVIDIAのモデル、API、安全性、障害、買収、サービス終了、価格・条件変更を確認する。セキュリティはCISA KEVのJSON、JVN／JPCERT、主要プロジェクト・ベンダー告知、公開調査フィードを一般検索より先に確認する。悪用確認、認証前RCE、サプライチェーン侵害は不採用でも`findings`へ理由を残す。軽微なCVEやベンチマーク順位だけで一般枠を埋めない。

VCFは`config/monitoring-sources.json`のVCF項目をすべて確認し、VMSA、KB、TechDocs、リリースノート、Service Status、互換性、HCL、ライフサイクル、Avi、vDefend、VCF Operationsに加え、公式ブログ・ニュースルームの製品・ポートフォリオ発表を独立した経路として扱う。新しいエディションやパッケージの追加、ライセンス体系と価格モデル、製品の追加・終了・改名、販売終了とサポート期限、提供地域や購入条件の変更は、セキュリティ情報でなくてもfindingsとして必ず評価し、採用しない場合も理由を記録する。過去に発表されたが未掲載のままの重要な公式発表は、期間外を理由に参考扱いで終えず、詳細の判明や続報が出た時点で`lateInclusion`として改めて評価する。William Lam、Duncan Epping、運用者コミュニティは現場情報の入口に使い、仕様、版、脆弱性、サポート可否を公式資料でも照合する。取得不能は`restricted`または`failed`として実態、時刻、URLを個別記録し、処理終了時刻や同じ注記を全件へコピーしない。

ミーム・流行動画は0〜3件を目安とし、発祥、元素材、音源、拡散経路、広告・仕込み、権利を確認できたものだけ扱う。元動画、画像、音源、歌詞、サムネイルは転載せず、二次被害のおそれがある題材は採用しない。

## 5. 全記事の編集基準

想定読者はソフトウェア、インフラ、AI、セキュリティの基礎があるエンジニア本人である。初学者向けの「XとはYです」を避け、既知の概念へ短く接続してから、今回固有の構造、障害モード、規模、費用、運用判断を説明する。専門外の科学、経済、制度、個別業界は具体例と数値比較で橋渡しする。

各記事は次を満たす。

- 独自タイトル。概要は結論・主要事実・適用範囲の3段落、合計240文字以上。第1段落だけで誰が何をして何が変わったか分かる。
- Top 5の`comment`は300文字以上。概要を言い換えず、背景、仕組み、比較、影響、判断軸を含む詳細な解説とし、独自の見立て・評価・見通し（追加観点）はここだけに書く。
- 非Top 5の`comment`は150文字以上の「中立的な分析と補足」とし、事実の位置づけ、理解に必要な背景事実、一次資料に基づく補足だけを書く。独自の見立て・評価・見通し・推奨は書かない。全記事の上限は1000文字。
- `attentionAnalysis`（注目理由と影響）と`articleDetail`（事実に基づく詳細・補足）はTop 5かどうかにかかわらず全記事で維持する。`articleDetail`は具体情報がある欄だけ使い、情報がなければ空配列とし、一般論や監視予定で埋めない。
- 数字には母数、期間、定義、比較対象を付ける。研究は対象数、方法、相関と因果、査読状況を確認する。
- 主張を事実、当事者説明、解釈、推定、予測に分け、一次資料と独立資料で照合する。根拠のある別解釈があれば重み付きで示し、偽のバランスは作らない。
- 「なぜ今起きたか」を調べ、公式理由、報道分析、編集上の推論を分ける。
- 概要、解説、詳細、注目理由、台本で同じ文や結論を再掲しない。結論の正本だけは概要第1段落、`articleDetail.conclusion`、`narration.result`で共有できる。
- 具体情報を増やさない留保、編集手順、監視予定、意味のない三項目以上の列挙を削除する。
- 前日7時より前の記事は`lateInclusion`を付ける。既掲載事案は実質更新または明確な再燃がある場合だけ`followUp`と`relatedArticleIds`を付け、元掲載日と変化を冒頭で示す。「再確認：」は使わない。

記事本文、`summary`、`comment`、`articleDetail`、台本を、ループ、共通テンプレート、文字列置換、`.repeat()`、記事名だけを差し替える生成スクリプトで作ってはいけない。スクリプトへ任せるのは候補取得、メタデータ整理、重複検出、検証、音声処理だけとし、編集本文は採用した各記事の根拠メモから個別に書く。

採用記事は必ず1件ずつ完結させる。次の完了ゲートを通してから次の記事へ進む。(1)確定台帳の該当行と一次資料だけを開く。(2)数値、固有名詞、日付を`generated/articles/YYYY-MM-DD/anchors/<article-id>.json`へアンカー事実として保存する。アンカーファイルが存在しない記事は未完了である。(3)`summary`、`articleDetail`、`comment`の順に本文を書く。本文中に新しい英字固有名詞・製品名・ライブラリ名・略語が出た時点で、公式または信頼できる読みを確認して`config/pronunciations.json`へ登録する。(4)本文のsummary第1段落と`articleDetail.conclusion`から、その記事固有の見出しを最後に付ける。仮置きの「本日の更新」などの見出しで記事ファイルを保存せず、仮置き見出しのまま単体検証へ進まない。(5)完成した版JSONの記事オブジェクトそのものを`generated/articles/YYYY-MM-DD/<article-id>.json`へ保存する。(6)まず`articleSchema`による単体検証、続けて`npm run edition:guard -- --single generated/articles/YYYY-MM-DD/<article-id>.json`を通す。(7)独立した記事単位監査でアンカーと数値・固有名詞・題材の一致を確認する。アンカー保存、本文、本文から付けた見出し、両方の単体検証、記事単位監査のすべてが通過するまで次の記事に進まない。Top 5は台本を保存後に同じ単体検証と監査を再実行し、通過した記事だけを台本を含めて凍結する。修正が必要なら該当記事ファイルだけを直す。

版JSONを主担当が直接編集してはいけない。すべての記事が凍結された後、`npm run edition:assemble -- --date YYYY-MM-DD`の生成物だけを`data/daily/YYYY-MM-DD.json`とする。これは本文生成ではなく結合であり、日付別の本文生成スクリプトを作って全件再生成する禁止を回避するものではない。18件以上で品質を維持できない候補しか残らなければ、短縮理由を記録して完成工程へ進む。

企業・雇用、制度・規制、ボット判定、科学、AIモデル・製品世代、セキュリティ事故などに該当する記事だけ、`docs/topic-editorial-playbooks.md`の該当節を読む。すべての専門ルールを毎回読み込まない。

コメント欄やソーシャル反応は追加検証の入口に使い、事実や一般世論の根拠にしない。反響値は実測値と確認時刻を記事・サイト・RSSに残すが、音声では「今朝の時点で」と簡潔にする。値がなければ編集手順を読み上げず、記事概要へ直接進む。

## 6. Top 5台本

Top 5のnarrationは、その記事の本文とアンカーの単体検証・記事単位監査が通過してから、その記事だけを見て作成する。配役は記事ごとにランダムに決め、連続する記事で同じ配役になってもよい。決定的な配役ローテーションは使わない。narrationを保存後に同じ記事の単体検証と監査を再実行してから凍結する。

Top 5ごとに主要主張、裏付け、反応から得た検証論点、別解釈、未確認事項、現時点の評価を内部整理する。台本では必要な要素だけを自然につなぎ、型を全部読み上げない。ニュースを入口に周辺知識を広げる論点は原則2つまでとし、主文に必要な短い背景は文中へ織り込む。問いを読み上げる自問自答、「ここで気になるのは」「ここがポイント」の定型句、不明・未確定だけの区間は作らない。

役割は紹介、解説、追加視点の最大3つ。無価値な3役目は省き、同じ説明を別キャスターに繰り返させない。自然な「です・ます」調で話し、常体の「である」「難しい。」「確定しない。」で閉じない。ずんだもんは最初と最後を中心に、くどくない範囲で「のだ」を使う。

英字名、製品名、ライブラリ名、略語は公式または信頼できる発音を確認し、未登録語を`config/pronunciations.json`へ追加する。語中に読点や中黒を入れず、URLや略語も一語として読ませる。英語引用は1日1〜2か所、5〜20語を上限とし、発音用カタカナを英語の意味上のまとまりで2〜4区間に分け、訳を一度だけ添える。国名は音声で「アメリカ」「イギリス」など日常的な呼び方にする。

## 7. 監査、音声、公開

全記事の単体検証と記事単位監査が通過したら、`npm run edition:assemble -- --date YYYY-MM-DD`で版JSONを結合し、`npm run validate:data`を通す。主担当は版JSONを直接編集しない。レビュー指摘の修正は該当する個別記事ファイルだけに行い、assembleと検証を再実行する。続けて`npm run media:script -- --date YYYY-MM-DD --audit-only`を実行する。レビュー専用モードではVOICEVOX設定と発音辞書を読まず、内容確認用の仮話者だけで台本を作る。続けて`npm run media:audit-bundle -- --date YYYY-MM-DD`を実行する。レビューバンドルは全記事の概要と結論を含み、全文精査はTop 5、機械的なリスク記事、その日の年月日から決める非Top 5の5件サンプルに限定する。独立編集レビューは`docs/editorial-audit-rubric.md`だけを基準にする。

独立編集レビューの指摘を反映し、機械検査と主担当の差分確認を終えたら、`docs/media-production-policy.md`、`config/voicevox.json`、`config/pronunciations.json`を読み、正式な`npm run media:script -- --date YYYY-MM-DD`、`npm run media:voicevox -- --date YYYY-MM-DD`、`npm run media:render -- --date YYYY-MM-DD`を実行する。VOICEVOXが停止中ならローカルアプリを一度起動してAPI応答を待ち、起動不能、未登録読み、音声検証失敗の場合だけ音声を公開せず既存公開版を維持する。完成M4Aのデコード、約-16 LUFS、クレジット、メタデータ、Range再生を確認し、Releaseと`config/published-media.json`を更新する。

`npm run check:all`を1回実行し、すべて成功した場合だけ意図したファイルを選択的にcommit、push、CI、Pages公開へ進む。個別コマンドを成功確認のため繰り返さない。Git authorとcommitterは`floortable <floortable@users.noreply.github.com>`を使う。公開ページ、RSS、Release音声まで確認する。

CIとPagesの失敗だけでなく警告と注釈も確認する。廃止日、強制移行、セキュリティ、互換性に関わる新しい警告は、CI成功だけを理由に放置せず、公式の移行先が利用可能なら対応する。将来のホストイメージ変更など利用者側の変更が不要な通知は月次保守の監視対象へ回す。

通常判断は途中承認を求めず完了まで進める。新しい認証・権限、追加課金、公開範囲拡大、回復困難な破壊操作、本人だけが確定できる権利・事実だけ確認を求める。公開を止めてよいのは、差し替えてもTop 5の中心事実を確認できない、必須検査が失敗する、音声を生成・検証できない、権利・安全上公開できない場合だけとする。記事数不足、レビュー指摘、取得不能な非Top 5は縮小・削除・差し替えで回復し、停止理由にしない。成功または通常の無変更では通知しない。

主担当は、作業量の見積り、経過時間、残りコンテキスト、途中の候補不足、または「安全に完走する時間がない」という自己判断を理由に、日次処理を終了・保留・引き継ぎ待ちにしてはいけません。途中で失敗や情報不足を見つけたら、まず限定的な再取得、代替経路、候補の差し替え、記事数の縮小、局所的な修正、または検査・音声工程の再試行で回復し、上記の明示的な公開停止条件に該当することを具体的に確認した場合に限って既存公開版を維持します。停止時は、失敗URLの列挙ではなく、どの停止条件に該当したか、代替一次資料・別報道・差し替え候補を何件試したか、15件へ縮小しても何が不足したか、どのコマンドまたは検証が失敗したかを記録します。これらを試さず「十分に裏付けられない」「品質を下げたくない」と総括して終了してはいけません。

実行中に、利用者向けの進捗報告、部分完了報告、ステータス通知、または最終応答を返して処理を終了してはいけません。応答を返せるのは、公開ページ、RSS、Release音声、CI、Pages、再生確認まで成功した後、または本書で定めた公開停止条件をコマンド出力とともに満たした後だけです。途中で利用者から「止まっていないか」「続けて」と尋ねられた場合も、状態説明だけで区切らず、直ちに同じ実行の次の未完了工程へ戻ること。未公開の下書き、検査通過、監視完了、音声生成前、commit前は完了ではなく、作業を終了する根拠にしてはいけません。
