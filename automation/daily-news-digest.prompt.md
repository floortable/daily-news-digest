# 毎日の注目記事約30選＋VCF運用監視

毎日7時（Asia/Tokyo）、当日版の記事、Top 5音声、RSS、サイトを完全自動で更新する。作業対象はリポジトリのルートとし、有料API、従量課金サービス、追加課金は使わない。動画とBGMなし版は生成しない。

## 1. 開始と既知問題

安全に最新の`main`へ同期し、作業ツリーにある利用者の変更を保護する。`reviews/README.md`と最新の`reviews/YYYY-MM-DD.md`を読む。GitHubでは`is:issue is:open in:title "[Museレビュー]"`に一致するIssueの状態、最新コメント、レビュー正本にない追加チェック項目だけを確認する。同じ日付のレビュー本文がローカルにあれば、Issueへ転載された同一本文を再読しない。外部レビューやGitHubを取得できないことだけを理由に生成を停止せず、公開前の独立監査を必須とする。

レビューは再発防止に使うが、指摘を鵜呑みにせず、現行データ、一次資料、検査コードで再現する。レビューの文章、数値、評価をニュースの事実や記事材料として転記してはいけません。レビューや監査の存在を公開版の正しさの根拠にしない。強化案は誤検知と運用負担を評価し、再現可能なものだけ恒久対策にする。Issueの更新やクローズはMuseへ委ねる。

## 2. モデルとコンテキスト

毎回新しい独立ジョブを`model: "gpt-5.6-terra"`、`reasoning_effort: "medium"`で実行する。過去の実行チャットを継承せず、現行ファイルを正本とする。調査、選定、執筆、修正、公開は主担当1体が順番に行い、これらのためにサブエージェントを起動しません。定型確認、候補整理、重複検査、検証、音声処理はスクリプトへ任せ、成功ログや一覧をモデルへ再掲しない。

サブエージェントは公開前の独立監査1体だけとする。`fork_turns: "none"`、`model: "gpt-5.6-sol"`、`reasoning_effort: "low"`で起動し、`docs/editorial-audit-rubric.md`と生成済み監査バンドルだけを渡す。最新レビューや主担当の評価を渡さず、記事本文やログ全文をルートへ再掲させません。監査は原則1回で、Top 5の結論を大きく直した場合だけ同じ担当へ変更箇所を1回再確認させ、当日版全体を再読させません。新しい監査エージェントを繰り返し起動してはいけません。利用不能時はTerra、次にLunaを使い、6系へ自動昇格しません。

## 3. 候補台帳を先に完成させる

最初に`npm run candidates:collect -- --date YYYY-MM-DD`を実行し、`generated/candidates/YYYY-MM-DD.json`を候補台帳の土台にする。失敗したフィードだけブラウザーで代替確認する。`config/monitoring-sources.json`の必須巡回先、前日版の続報候補、Hacker News、はてなブックマーク、一般報道、ソーシャル発見を一巡し、候補ごとに見出し、URL、公開日時、出来事、一次資料、話題性、重複先、暫定採否を1行で記録する。

重要候補を`included`、`deferred`、`not-relevant`へ分類するまで本文を書かない。必須巡回後の一般検索は不足分を補う一巡に限定し、同じ検索語の言い換えを繰り返さない。候補固定後の検索は採用記事の事実確認、背景、比較、反響の裏付けだけに使う。

一般ニュースは通常25〜35件、30件前後とするが、弱い記事や検証不能な記事で埋めない。25件未満なら候補台帳と`monitoringReview.findings`を照合し、高重要度の未分類、見落とし、一次資料を取得できる候補が残っていないことを確認してから、探索数と除外理由を`selectionShortfallReason`へ具体的に書く。

分野と媒体の詳細基準は`docs/selection-policy.md`、巡回記録は`docs/monitoring-policy.md`に従う。一般ニュースのテクノロジーとセキュリティは合計40％以下。同一媒体は原則4件以下。VCF専門枠は一般枠と分離して0〜5件とし、新情報がなければ0件にする。

Top 5は5件、4分野以上、4媒体以上から選ぶ。技術・セキュリティは2件以下、政府公式発表は2件以下、Hacker News・はてな・ソーシャル由来を2件以上、文化・暮らし・科学・スポーツ・地域・人物・ネット文化から1件以上含める。個人リスナーは野球に関心がないため、競技結果や移籍などの野球記事をTop 5へ通常採用しない。

## 4. 横断監視

AIはOpenAI、Anthropic、Google／DeepMind、Microsoft、Meta、NVIDIAのモデル、API、安全性、障害、買収、サービス終了、価格・条件変更を確認する。セキュリティはCISA KEVのJSON、JVN／JPCERT、主要プロジェクト・ベンダー告知、公開調査フィードを一般検索より先に確認する。悪用確認、認証前RCE、サプライチェーン侵害は不採用でも`findings`へ理由を残す。軽微なCVEやベンチマーク順位だけで一般枠を埋めない。

VCFは`config/monitoring-sources.json`のVCF項目をすべて確認し、VMSA、KB、TechDocs、リリースノート、Service Status、互換性、HCL、ライフサイクル、Avi、vDefend、VCF Operationsを別経路として扱う。William Lam、Duncan Epping、運用者コミュニティは現場情報の入口に使い、仕様、版、脆弱性、サポート可否を公式資料でも照合する。取得不能は`restricted`または`failed`として実態、時刻、URLを個別記録し、処理終了時刻や同じ注記を全件へコピーしない。

ミーム・流行動画は0〜3件を目安とし、発祥、元素材、音源、拡散経路、広告・仕込み、権利を確認できたものだけ扱う。元動画、画像、音源、歌詞、サムネイルは転載せず、二次被害のおそれがある題材は採用しない。

## 5. 全記事の編集基準

想定読者はソフトウェア、インフラ、AI、セキュリティの基礎があるエンジニア本人である。初学者向けの「XとはYです」を避け、既知の概念へ短く接続してから、今回固有の構造、障害モード、規模、費用、運用判断を説明する。専門外の科学、経済、制度、個別業界は具体例と数値比較で橋渡しする。

各記事は次を満たす。

- 独自タイトル。概要は結論・主要事実・適用範囲の3段落、合計240文字以上。第1段落だけで誰が何をして何が変わったか分かる。
- `comment`は300文字以上で、概要を言い換えず、背景、仕組み、比較、影響、判断軸のうち有用な理解を増やす。
- `articleDetail`は具体情報がある欄だけ使う。情報がなければ空配列とし、一般論や監視予定で埋めない。
- 数字には母数、期間、定義、比較対象を付ける。研究は対象数、方法、相関と因果、査読状況を確認する。
- 主張を事実、当事者説明、解釈、推定、予測に分け、一次資料と独立資料で照合する。根拠のある別解釈があれば重み付きで示し、偽のバランスは作らない。
- 「なぜ今起きたか」を調べ、公式理由、報道分析、編集上の推論を分ける。
- 概要、解説、詳細、注目理由、台本で同じ文や結論を再掲しない。結論の正本だけは概要第1段落、`articleDetail.conclusion`、`narration.result`で共有できる。
- 具体情報を増やさない留保、編集手順、監視予定、意味のない三項目以上の列挙を削除する。
- 前日7時より前の記事は`lateInclusion`を付ける。既掲載事案は実質更新または明確な再燃がある場合だけ`followUp`と`relatedArticleIds`を付け、元掲載日と変化を冒頭で示す。「再確認：」は使わない。

企業・雇用、制度・規制、ボット判定、科学、AIモデル・製品世代、セキュリティ事故などに該当する記事だけ、`docs/topic-editorial-playbooks.md`の該当節を読む。すべての専門ルールを毎回読み込まない。

コメント欄やソーシャル反応は追加検証の入口に使い、事実や一般世論の根拠にしない。反響値は実測値と確認時刻を記事・サイト・RSSに残すが、音声では「今朝の時点で」と簡潔にする。値がなければ編集手順を読み上げず、記事概要へ直接進む。

## 6. Top 5台本

Top 5ごとに主要主張、裏付け、反応から得た検証論点、別解釈、未確認事項、現時点の評価を内部整理する。台本では必要な要素だけを自然につなぎ、型を全部読み上げない。ニュースを入口に周辺知識を広げる論点は原則2つまでとし、主文に必要な短い背景は文中へ織り込む。問いを読み上げる自問自答、「ここで気になるのは」「ここがポイント」の定型句、不明・未確定だけの区間は作らない。

役割は紹介、解説、追加視点の最大3つ。無価値な3役目は省き、同じ説明を別キャスターに繰り返させない。自然な「です・ます」調で話し、常体の「である」「難しい。」「確定しない。」で閉じない。ずんだもんは最初と最後を中心に、くどくない範囲で「のだ」を使う。

英字名、製品名、ライブラリ名、略語は公式または信頼できる発音を確認し、未登録語を`config/pronunciations.json`へ追加する。語中に読点や中黒を入れず、URLや略語も一語として読ませる。英語引用は1日1〜2か所、5〜20語を上限とし、発音用カタカナを英語の意味上のまとまりで2〜4区間に分け、訳を一度だけ添える。国名は音声で「アメリカ」「イギリス」など日常的な呼び方にする。

## 7. 監査、音声、公開

記事完成後に`npm run media:script -- --date YYYY-MM-DD`を実行する。この時点ではVOICEVOX合成をしない。続けて`npm run media:audit-bundle -- --date YYYY-MM-DD`を実行する。監査バンドルは全記事の概要と結論を含み、全文精査はTop 5、機械的なリスク記事、その日の年月日から決める非Top 5の5件サンプルに限定する。独立監査は`docs/editorial-audit-rubric.md`だけを基準にする。

記事と台本の独立監査が合格してから、`docs/media-production-policy.md`、`config/voicevox.json`、`config/pronunciations.json`を読み、`npm run media:voicevox -- --date YYYY-MM-DD`、`npm run media:render -- --date YYYY-MM-DD`を実行する。監査不合格、未登録読み、VOICEVOX停止、音声検証失敗なら音声を公開せず既存公開版を維持する。完成M4Aのデコード、約-16 LUFS、クレジット、メタデータ、Range再生を確認し、Releaseと`config/published-media.json`を更新する。

`npm run check:all`を1回実行し、すべて成功した場合だけ意図したファイルを選択的にcommit、push、CI、Pages公開へ進む。個別コマンドを成功確認のため繰り返さない。Git authorとcommitterは`floortable <floortable@users.noreply.github.com>`を使う。公開ページ、RSS、Release音声まで確認する。

CIとPagesの失敗だけでなく警告と注釈も確認する。廃止日、強制移行、セキュリティ、互換性に関わる新しい警告は、CI成功だけを理由に放置せず、公式の移行先が利用可能なら対応する。将来のホストイメージ変更など利用者側の変更が不要な通知は月次保守の監視対象へ回す。

通常判断は途中承認を求めず完了まで進める。新しい認証・権限、追加課金、公開範囲拡大、回復困難な破壊操作、本人だけが確定できる権利・事実だけ確認を求める。安全に完成できない場合は既存公開版を壊さず停止し、ユーザー対応が必要な失敗だけ通知する。成功または通常の無変更では通知しない。
